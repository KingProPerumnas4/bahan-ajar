1. Review Pemrograman Website 1 dan Di Mana Batasnya

Pada Pemrograman Website 1, Anda sudah membangun halaman web dengan tiga bahan: HTML untuk menyusun isi, CSS untuk mengatur tampilan, dan JavaScript untuk membuat halaman merespons perbuatan pengguna. Halaman semacam itu sudah bisa terlihat bagus dan terasa hidup: menu bisa dibuka-tutup, gambar bisa bergeser, dan hasil hitungan bisa muncul tanpa halaman dimuat ulang.

Namun ada satu hal yang perlu disadari tentang semua itu: seluruhnya berjalan di komputer pengunjung. Ketika sebuah halaman dibuka, berkas HTML, CSS, dan JavaScript dikirim ke browser, lalu browser yang menjalankannya. Tidak ada bagian dari program itu yang bekerja di tempat lain. Akibatnya muncul empat batasan yang tidak bisa diatasi dengan menambah JavaScript sebanyak apa pun.

  1. Data tidak bertahan. Nilai yang tersimpan di variabel hilang begitu halaman dimuat ulang. Bahkan bila dipaksa disimpan di localStorage, data itu hanya ada di satu browser pada satu komputer.
  2. Data tidak dapat dibagi. Apa yang diisi seorang pengguna tidak akan pernah terlihat oleh pengguna lain, karena tidak ada tempat bersama untuk menampungnya.
  3. Semua kode terbuka dan dapat diubah. Pengunjung dapat membaca seluruh JavaScript halaman Anda, mengubah nilainya, atau melewati pemeriksaan yang Anda tulis. Karena itu, apa pun yang penting tidak boleh hanya diperiksa di browser.
  4. Tidak ada penjaga pintu. Tanpa pihak lain yang memutuskan siapa berhak melihat apa, gagasan seperti login, peran admin, dan halaman terbatas tidak mungkin diwujudkan dengan sungguh-sungguh.
Analogi dunia nyata: Pemrograman Website 1 seperti papan tulis di ruang kelas. Anda bisa menulis, menghapus, dan mengatur tata letaknya sesuka hati, dan hasilnya terlihat bagus bagi siapa pun yang sedang berada di ruangan itu. Tetapi papan tulis akan dihapus, isinya tidak tercatat, dan orang di ruangan sebelah tidak dapat melihatnya. 2. Client dan Server: Dua Peran, Dua Tugas

Istilah client dan server menunjuk pada peran, bukan pada merek atau bentuk perangkat. Client adalah pihak yang meminta. Server adalah pihak yang menunggu permintaan lalu menjawabnya. Browser Anda adalah client. Program Express yang akan Anda tulis mulai Pertemuan 2 adalah server.

Yang perlu ditegaskan sejak awal: server hanyalah sebuah program yang sedang berjalan dan menunggu. Ia bukan lemari besi di ruang berpendingin, walaupun pada aplikasi sungguhan program itu memang dijalankan di komputer khusus. Selama masa belajar ini, server Anda berjalan di laptop Anda sendiri. Ketika sebuah program Node.js dijalankan dan ia menunggu di sebuah pintu bernomor, saat itulah laptop Anda menjadi server.

Analogi dunia nyata: bayangkan sebuah rumah makan. Pelanggan adalah client: ia menyebutkan apa yang diinginkan, lalu menunggu. Pelayan adalah server, dalam hal ini Express: ia menerima pesanan, tahu pesanan mana ditangani siapa, lalu mengantarkan hasilnya. Gudang bahan adalah database, yaitu MySQL: tempat bahan disimpan rapi, diambil saat dibutuhkan, dan tidak pernah dimasuki langsung oleh pelanggan. Perhatikan bahwa pelanggan tidak pernah masuk ke gudang sendiri, dan itu bukan kebetulan — itu adalah aturan keamanan yang sama persis dengan aturan pada aplikasi web.

Pertanyaan ini wajar muncul, sebab JavaScript sudah mampu banyak hal di browser. Ada empat alasan yang membuat sisi server tetap diperlukan.

Cara itu berarti nama pengguna dan kata sandi database ikut terkirim ke setiap pengunjung, sehingga siapa pun dapat membaca dan menghapus seluruh data. Database hanya dihubungi oleh server. Browser berbicara kepada server, dan server yang berbicara kepada database. Aturan ini tidak punya pengecualian di mata kuliah ini.

2.3 Alamat, host, dan port

Sepanjang semester ini Anda akan sering menjumpai alamat seperti http://localhost:3000/buku. Alamat itu terdiri dari empat bagian yang masing-masing punya arti.

  • http:// adalah protokol, yaitu aturan tata bahasa yang dipakai browser dan server agar saling mengerti.
  • localhost adalah host, yaitu komputer yang dituju. Nama localhost selalu berarti “komputer ini sendiri”, sehingga permintaan tidak keluar ke internet sama sekali.
  • 3000 adalah port, yaitu nomor pintu. Satu komputer bisa menjalankan banyak program yang menunggu sekaligus, dan nomor port membedakan permintaan itu ditujukan kepada program yang mana.
  • /buku adalah path, yaitu bagian yang menyatakan apa yang diminta. Inilah bagian yang akan Anda cocokkan dengan route pada Pertemuan 3.
Analogi dunia nyata: host adalah alamat gedung, port adalah nomor pintu pada gedung itu, dan path adalah nama ruangan yang ingin dituju. Kalau nomor pintunya salah, tidak ada yang membukakan meskipun gedungnya benar. Inilah sebab galat connection refused muncul saat server belum dijalankan: gedungnya ada, tetapi tidak ada seorang pun yang menunggu di pintu nomor 3000.

3. Siklus Request-Response

Seluruh isi mata kuliah ini berpusat pada satu pola yang berulang tanpa henti: browser mengirim request, server menjawab dengan response, lalu keduanya selesai. Satu klik tautan adalah satu siklus. Satu penekanan tombol kirim pada formulir adalah satu siklus. Setiap kali Anda memuat ulang halaman, siklus itu terjadi lagi dari awal.

Ada satu sifat pada pola ini yang perlu diingat sejak sekarang: server tidak pernah memulai. Ia tidak mengirim apa pun sebelum ada yang meminta. Selama tidak ada permintaan, program server hanya menunggu tanpa mengerjakan apa-apa. Karena itu, ketika sebuah aplikasi web terasa “tidak melakukan apa pun”, yang perlu dicari lebih dulu bukan kesalahan pada server, melainkan apakah permintaannya benar-benar terkirim.

3.1 Bentuk pesan request dan response

Request dan response sebenarnya hanyalah teks yang dikirim melalui jaringan, dengan susunan yang sudah dibakukan. Keduanya punya bentuk yang mirip: satu baris pembuka, beberapa baris keterangan yang disebut header, lalu bagian isi yang disebut badan pesan atau body.

Perhatikan bahwa pada gambar di atas tidak ada yang ajaib. Yang berpindah antara browser dan server hanyalah teks. Header Content-Type pada response itulah yang memberi tahu browser bagaimana isi harus diperlakukan: bila nilainya text/html maka isi digambar sebagai halaman, bila application/json maka isi dianggap data, dan bila image/png maka isi digambar sebagai gambar. Badan pesannya sendiri sama-sama hanya kumpulan huruf.

Karena itu, memahami maksud tiap metode sekarang akan sangat memudahkan nanti.

Isi permintaan POST dikirim pada badan pesan, sehingga tidak muncul di alamat. Itulah sebab formulir login selalu memakai POST: kata sandi tidak boleh tercetak di kolom alamat.

3.3 Kode status: jawaban singkat sebelum isinya dibaca

Setiap response membawa satu bilangan tiga angka yang menyatakan hasil permintaan. Angka pertamanya sudah cukup untuk mengetahui garis besarnya, dan kebiasaan membaca angka ini akan menghemat banyak waktu Anda saat mencari kesalahan nanti.

3.4 Satu halaman, banyak request

Satu halaman web yang tampak sebagai satu benda utuh sesungguhnya hasil dari puluhan siklus request-response. Browser mula-mula meminta dokumen HTML-nya. Setelah HTML itu dibaca, browser menemukan rujukan ke berkas CSS, berkas JavaScript, gambar, dan huruf, lalu meminta semuanya sebagai permintaan terpisah. Barulah setelah itu halaman tampak utuh.

Kenyataan ini bukan hal sepele, dan Anda akan membuktikannya sendiri pada praktik Bab 5. Kenyataan ini pula yang menjelaskan mengapa panel Network berisi banyak baris hanya untuk satu halaman, dan mengapa fetch() pada Pertemuan 14 dapat memperbarui sebagian halaman: fetch() sekadar menambahkan satu permintaan lagi tanpa mengulang permintaan dokumen utamanya.

3.5 HTTP tidak mengingat: sifat stateless

Sifat berikut ini termasuk yang paling sering membingungkan pemula, dan sekaligus menjadi alasan keberadaan seluruh materi Pertemuan 12. HTTP bersifat stateless, artinya setiap permintaan berdiri sendiri. Server tidak menyimpan ingatan apa pun tentang permintaan sebelumnya. Setelah sebuah response terkirim, hubungan itu selesai, dan permintaan berikutnya dari orang yang sama diterima seolah-olah datang dari orang yang belum pernah dikenal.

Analogi dunia nyata: bayangkan sebuah loket yang petugasnya berganti setiap kali Anda datang, dan petugas baru itu tidak diberi tahu apa pun tentang kunjungan Anda sebelumnya. Agar tetap dilayani, Anda harus membawa sesuatu yang membuktikan siapa Anda, misalnya kartu antrean. Dalam aplikasi web, kartu antrean itulah yang disebut cookie, dan catatan di sisi loket yang bersesuaian dengan kartu itu disebut session.

Karena itu, fitur login tidak bekerja dengan cara “server mengingat bahwa Anda sudah masuk”. Yang sesungguhnya terjadi adalah browser menyertakan tanda pengenal pada setiap permintaan berikutnya, dan server memeriksa tanda itu setiap kali. Mekanismenya dibahas tuntas pada Pertemuan 12, tetapi sifat stateless-nya perlu dipahami sekarang, sebab tanpa itu login akan terasa sebagai keajaiban dan bukan sebagai rangkaian langkah yang dapat ditelusuri.

4. Peran Express, Peran MySQL, dan Arsitektur Aplikasi

Tiga nama akan menemani seluruh semester ini: Node.js, Express, dan MySQL. Ketiganya sering disebut bersamaan sehingga mudah tertukar, padahal tugasnya jelas berbeda. Bagian ini memisahkannya satu per satu, lalu menyatukannya kembali menjadi satu gambar alur.

4.1 Node.js: JavaScript di luar browser

Sampai semester lalu, JavaScript hanya Anda kenal sebagai bahasa yang dijalankan browser. Node.js adalah program yang memungkinkan JavaScript dijalankan langsung oleh sistem operasi, tanpa browser sama sekali. Dengan Node.js, JavaScript memperoleh kemampuan yang tidak pernah dimilikinya di dalam browser: membaca dan menulis berkas di cakram, membuka koneksi jaringan, dan menunggu permintaan masuk di sebuah port.

Keuntungan pilihan ini bagi Anda cukup besar. Bahasa yang dipakai di sisi browser dan di sisi server menjadi sama, sehingga tidak ada bahasa baru yang harus dipelajari dari nol pada minggu-minggu pertama. Yang baru adalah tempat kode itu berjalan dan tugas yang diembannya.

4.2 Express: yang menerima permintaan dan menentukan jawabannya

Node.js sendiri sudah mampu menerima permintaan HTTP, tetapi caranya masih terlalu mentah: setiap permintaan datang sebagai satu tumpukan teks yang harus Anda pilah sendiri. Express adalah pustaka tambahan yang merapikan pekerjaan itu. Dengan Express, Anda cukup menyatakan pasangan “metode dan alamat” beserta fungsi yang menanganinya, lalu Express mengurus sisanya.

Pasangan itulah yang disebut route. Sebuah aplikasi yang sudah jadi umumnya berisi belasan route, misalnya GET /buku untuk menampilkan daftar, POST /buku untuk menyimpan yang baru, dan GET /login untuk menampilkan formulir masuk. Selain route, Express juga menyediakan middleware, yaitu fungsi yang dijalankan sebelum route dan dapat memeriksa, mengubah, atau menolak permintaan — misalnya untuk mencatat log atau menolak pengunjung yang belum login. Keduanya dibahas rinci pada Pertemuan 3.

Analogi dunia nyata: Express seperti resepsionis yang memegang daftar. Ia tidak menyelesaikan pekerjaan sendiri, tetapi tahu persis siapa yang menangani apa. Ketika ada tamu bertanya soal peminjaman, ia meneruskan ke bagian peminjaman. Ketika ada tamu bertanya soal alamat yang tidak ada dalam daftarnya, ia menjawab dengan sopan bahwa hal itu tidak ada — dan jawaban itulah yang sampai ke pengunjung sebagai 404.

4.3 MySQL: tempat data disimpan dengan rapi

MySQL adalah sistem database relasional. Kata relasional berarti data disimpan dalam tabel yang saling berhubungan. Setiap tabel punya kolom yang tetap, misalnya tabel buku memiliki kolom id, judul, dan penulis. Setiap catatan menjadi satu baris. Untuk mengambil, menambah, mengubah, atau menghapus baris, dipakai bahasa khusus bernama SQL.

Pertanyaan yang wajar: mengapa tidak cukup menyimpan data di dalam berkas teks biasa? Sebab MySQL menangani hal-hal yang sangat merepotkan bila dikerjakan sendiri: mencari satu baris di antara ratusan ribu baris dengan cepat, melayani beberapa pengguna yang menulis pada saat yang sama tanpa data saling menimpa, menolak data yang bentuknya tidak sesuai, dan menjaga hubungan antar tabel tetap masuk akal. Semua itu dibahas mulai Pertemuan 5.

Analogi dunia nyata: berkas teks seperti tumpukan catatan lepas di atas meja — cepat untuk satu dua lembar, tetapi mustahil ditelusuri begitu jumlahnya ratusan dan ada beberapa orang yang menulis di atasnya bersamaan. Database seperti buku induk yang berkolom tetap, bernomor, dan punya aturan pengisian: lebih kaku, tetapi justru karena itu masih terbaca sepuluh tahun kemudian.

4.4 Tiga lapisan dan letak setiap pertemuan

Bila ketiganya disusun, terbentuk tiga lapisan yang menjadi kerangka seluruh mata kuliah ini. Gambar berikut sekaligus memperlihatkan pertemuan mana yang mengerjakan lapisan mana, sehingga setiap topik yang muncul nanti punya tempatnya.

Dua pertemuan tidak muncul pada gambar itu, yaitu Pertemuan 8 dan 16, sebab keduanya adalah penilaian yang menguji ketiga lapisan sekaligus. Pertemuan 15 juga tidak terikat pada satu lapisan, karena debugging dan deployment menyentuh semuanya.

4.5 Alur lengkap: browser → server → database → browser

Inilah inti Pertemuan 1, dan inilah satu gambar yang paling perlu Anda ingat dari hari ini. Perhatikan bahwa perjalanannya bolak-balik: permintaan bergerak ke kanan, jawaban kembali ke kiri, dan siklusnya berakhir di tempat ia dimulai.

Agar tidak berhenti sebagai gambar, mari kita telusuri satu kejadian yang sangat biasa: seorang petugas menekan tautan Daftar Buku. Tujuh langkah berikut terjadi dalam waktu kurang dari sedetik.

  1. Pengguna menekan tautan Daftar Buku pada halaman.
  2. Browser menyusun sebuah request, yaitu GET /buku, mengirimkannya ke server, lalu menunggu.
  3. Express menerima request itu dan mencari di daftar route-nya, mana yang cocok dengan metode GET dan alamat /buku.
  4. Fungsi pada route tersebut dijalankan, dan fungsi itu mengirim query SELECT id, judul, penulis FROM buku ke MySQL.
  5. MySQL mencari baris-baris yang diminta lalu mengembalikannya kepada Express.
  6. Express mengubah baris-baris itu menjadi HTML atau JSON, lalu mengirimkannya sebagai response dengan kode status 200.
  7. Browser menerima response dan menggambar daftarnya di layar. Siklus selesai, dan server kembali menunggu tanpa mengingat apa pun.

Perhatikan bahwa langkah 3 sampai 6 adalah bagian yang harus Anda tulis sendiri, dan bagian itulah yang mengisi hampir seluruh Pertemuan 2 sampai 10. Langkah 1, 2, dan 7 dikerjakan oleh browser tanpa perlu Anda program. Dari sudut pandang ini, mata kuliah ini sesungguhnya hanya mengajarkan cara mengisi empat langkah di tengah.

Cara memakai alur ini saat mencari kesalahan. Jika sesuatu tidak berjalan, tentukan lebih dulu langkah keberapa yang gagal, jangan langsung mengubah kode. Tidak ada baris baru di panel Network berarti langkah 2 gagal, permintaannya bahkan tidak terkirim. Muncul 404 berarti langkah 3 gagal, route-nya tidak ditemukan. Muncul 500 berarti langkah 4 atau 5 gagal, biasanya query yang salah tulis. Halaman kosong dengan status 200 berarti langkah 6 berhasil tetapi isinya memang kosong. Kebiasaan menempatkan gejala pada langkah tertentu inilah yang dilatih khusus pada Pertemuan 15.

5. Implementasi Praktis: Menelusuri Siklus Request-Response yang Sungguhan

Aktivitas praktik Pertemuan 1 adalah membuktikan sendiri bahwa siklus pada Bab 3 dan alur pada Bab 4.5 benar-benar terjadi. Semuanya dikerjakan dari browser, tanpa memasang apa pun, dan tanpa menulis satu baris kode. Yang dipakai adalah peralatan pengembang atau developer tools, yaitu panel bawaan browser yang memperlihatkan seluruh permintaan yang keluar-masuk.

5.1 Tujuan praktik

  • Melihat dengan mata sendiri bahwa satu halaman terdiri dari banyak siklus request-response.
  • Membaca metode, alamat, kode status, dan jenis isi dari sebuah permintaan yang nyata.
  • Membuktikan bahwa alamat yang berbeda menghasilkan data yang berbeda, karena ada program dan penyimpanan di seberang sana.
  • Mengenali panel yang akan dipakai berulang kali sepanjang semester untuk memeriksa pekerjaan sendiri.

5.2 Membuka panel Network

Langkahnya sama pada Chrome, Edge, dan Brave. Pada Firefox namanya juga Network dengan susunan yang serupa.

  1. Tekan F12, atau Ctrl+Shift+I bila F12 tidak berfungsi. Pada macOS gunakan Cmd+Option+I.
  2. Pilih tab Network pada baris tab di bagian atas panel yang muncul.
  3. Biarkan panel itu tetap terbuka, lalu muat ulang halaman dengan Ctrl+R. Baris-baris akan mulai terisi.
Kesalahan yang paling sering terjadi pada langkah ini: panel dibuka setelah halaman selesai dimuat, sehingga daftarnya kosong dan tampak seperti tidak berfungsi. Panel Network hanya mencatat permintaan yang terjadi selagi ia terbuka. Jadi urutannya wajib: buka panel dulu, baru muat ulang halaman.

5.3 Praktik A: satu halaman, berapa banyak permintaan?

Bagian ini membuktikan pembahasan Bab 3.4.

  1. Buka sebuah halaman umum yang biasa Anda kunjungi, misalnya situs kampus atau id.wikipedia.org. Cukup dibaca seperti biasa; tidak ada yang perlu dikirim ke situs itu.
  2. Dengan panel Network terbuka, muat ulang halaman.
  3. Lihat keterangan di bagian bawah panel. Di sana tertulis jumlah permintaan dan besar data yang terkirim, misalnya 62 requests. Catat angkanya.
  4. Perhatikan kolom Type. Anda akan melihat nilai seperti document, stylesheet, script, font, dan image. Catat berapa banyak jenis yang berbeda yang Anda temukan.
  5. Klik tombol filter Doc di baris atas panel. Daftar menyusut, biasanya menjadi satu baris saja. Itulah dokumen HTML utama halaman tersebut, yaitu permintaan pertama dari seluruh rangkaian.
  6. Klik All untuk mengembalikan daftar seperti semula.

Yang perlu disadari dari langkah-langkah di atas: HTML utama datang lebih dulu dan sendirian, lalu segala berkas pendukung diminta menyusul karena disebutkan di dalam HTML itu. Urutan ini persis yang nanti terjadi pada aplikasi Anda sendiri.

5.4 Praktik B: membaca satu pesan request dan response

Bagian ini menghubungkan gambar pada Bab 3.1 dengan kejadian nyata.

  1. Masih pada halaman yang sama, klik baris paling atas pada daftar, yaitu baris berjenis document.
  2. Panel di sebelah kanan akan terbuka. Pilih tab Headers.
  3. Pada bagian General, catat tiga hal: Request URL, Request Method, dan Status Code. Bandingkan ketiganya dengan panel REQUEST pada gambar Bab 3.1.
  4. Buka bagian Response Headers. Cari Content-Type dan catat nilainya. Kemungkinan besar nilainya text/html.
  5. Buka bagian Request Headers. Cari Host dan User-Agent. Perhatikan bahwa browser mengirimkan banyak keterangan tentang dirinya tanpa pernah Anda perintahkan.
  6. Pindah ke tab Response. Di sana tampak isi yang dikirim server, yaitu teks HTML. Inilah badan pesan pada gambar Bab 3.1.
  7. Sekarang klik salah satu baris yang jenisnya stylesheet, lalu periksa Content-Type-nya. Nilainya berbeda, yaitu text/css. Bandingkan pula isi tab Response-nya.

Langkah terakhir itu penting: dengan protokol yang sama dan cara yang sama, server dapat mengirim jenis isi yang berbeda-beda. Yang membedakan perlakuan browser hanyalah header Content-Type. Pada Pertemuan 4 Anda akan mengatur nilai ini sendiri, ketika memilih apakah sebuah route menjawab dengan HTML atau dengan JSON.

5.5 Praktik C: membuktikan bahwa alamat menentukan data yang keluar

Dua praktik sebelumnya baru menyentuh dua kotak pertama pada alur Bab 4.5, yaitu browser dan server. Praktik ini menyentuh kotak ketiga. Kita akan memakai jsonplaceholder.typicode.com, sebuah layanan gratis yang memang disediakan untuk latihan semacam ini. Layanan itu menyimpan sekumpulan data contoh dan menjawab permintaan dalam bentuk JSON — persis seperti yang akan dilakukan API buatan Anda sendiri pada Pertemuan 14.

  1. Buka https://jsonplaceholder.typicode.com/posts/1 di sebuah tab baru, dengan panel Network tetap terbuka.
  2. Amati isi halaman. Yang tampak bukan HTML, melainkan data terstruktur dengan pasangan nama dan nilai. Catat nilai title-nya.
  3. Pada panel Network, klik baris permintaan itu dan catat Status Code serta Content-Type-nya. Bandingkan dengan yang Anda catat pada Praktik B — keduanya berbeda.
  4. Ubah alamatnya menjadi .../posts/2. Data yang muncul berbeda, padahal bentuk alamatnya sama. Catat nilai title yang baru.
  5. Ubah alamatnya menjadi .../posts/99999, yaitu nomor yang hampir pasti tidak ada. Catat apa yang muncul di halaman dan kode status yang tercatat di panel Network. Keduanya berubah.
  6. Terakhir, buka https://jsonplaceholder.typicode.com/posts tanpa nomor apa pun. Yang muncul adalah kumpulan data, bukan satu data.

Enam langkah itu sesungguhnya sudah memperagakan seluruh gagasan yang akan Anda bangun sendiri pada Pertemuan 9 dan 10. Bagian /posts adalah route untuk menampilkan daftar. Bagian /posts/1 adalah route dengan parameter, yaitu bagian alamat yang berubah-ubah dan dipakai untuk memilih satu baris tertentu dari database. Nomor yang tidak ada menghasilkan kode status yang berbeda, karena program di seberang sana memeriksa lebih dulu apakah datanya ditemukan. Kode untuk melakukan semua itu ada pada Bab 6.3 di bawah, dan panjangnya hanya beberapa baris.

5.6 Hasil yang diharapkan

Praktik ini dinyatakan berhasil bila empat hal berikut sudah Anda peroleh dan tercatat:

  • Sebuah angka jumlah permintaan untuk satu halaman biasa, yang hampir pasti jauh lebih dari satu.
  • Metode, alamat, kode status, dan Content-Type dari satu dokumen HTML yang nyata.
  • Dua nilai Content-Type yang berbeda dari dua jenis berkas yang berbeda.
  • Bukti bahwa /posts/1 dan /posts/2 memberi data yang berbeda, sedangkan nomor yang tidak ada memberi kode status yang berbeda pula.

Butir terakhir adalah yang paling penting untuk disadari: satu bagian kecil pada alamat menentukan baris mana yang diambil dari sebuah tabel. Inilah bentuk paling sederhana dari gagasan bahwa alamat adalah pertanyaan dan response adalah jawabannya, dan gagasan itulah yang nanti dipakai untuk menampilkan detail buku, mengubah data mahasiswa, atau menghapus satu barang inventaris.

6. Membaca Kode Server Pertama

Bagian ini memperlihatkan wujud kode dari alur yang baru saja Anda telusuri. Kode di bawah tidak dijalankan hari ini, sebab Node.js dan Express baru dipasang pada Pertemuan 2. Hari ini kode itu hanya dibaca, dengan satu sasaran: mengenali bagian mana yang menerima permintaan dan bagian mana yang mengirim jawaban. Bila hari ini Anda sudah dapat menunjuk kedua bagian itu, Pertemuan 2 akan terasa jauh lebih ringan.

6.1 Server Express yang paling sederhana

Program berikut adalah keseluruhan sebuah server web. Panjangnya sembilan baris, dan begitu dijalankan ia sudah dapat melayani permintaan dari browser.

const express = require('express');
const app = express();

app.get('/', (req, res) => {
  res.send('<h1>Halo dari server</h1>');
});

app.listen(3000, () => {
  console.log('Server berjalan di http://localhost:3000');
});

Setelah program itu dijalankan dan alamat http://localhost:3000 dibuka di browser, tulisan Halo dari server akan muncul di layar. Yang perlu disadari: teks HTML itu tidak berasal dari berkas mana pun. Tidak ada berkas index.html di dalam proyek tersebut. HTML-nya disusun oleh program pada saat permintaan datang — dan tepat inilah yang dimaksud “dinamis” pada Bab 1.1.

Ingat pembagiannya: console.log() berbicara kepada Anda sebagai pemrogram melalui terminal, sedangkan res.send() berbicara kepada pengguna melalui browser. Sepanjang semester ini Anda perlu membiasakan diri memandang dua jendela sekaligus: browser untuk melihat hasil, dan terminal untuk melihat apa yang terjadi di dalam server.

6.3 Ketika database ikut terlibat

Program berikut adalah bentuk lengkap dari alur Bab 4.5, yaitu route yang benar-benar mengambil data dari MySQL. Program ini adalah gambaran akhir dari Pertemuan 7, jadi tidak ada tuntutan untuk memahaminya sekarang. Bacalah sebagai peta, bukan sebagai bahan hafalan.

const express = require('express');
const mysql = require('mysql2/promise');

const app = express();

const db = mysql.createPool({
  host: 'localhost',
  user: 'root',
  password: process.env.DB_PASSWORD,
  database: 'perpustakaan'
});

app.get('/buku', async (req, res) => {
  const [rows] = await db.query('SELECT id, judul, penulis FROM buku');
  res.json(rows);
});

app.listen(3000);

Lima hal terjadi di dalamnya, dan kelimanya bersesuaian dengan langkah 3 sampai 6 pada Bab 4.5. Pertama, mysql.createPool menyiapkan sekumpulan koneksi ke database sehingga tidak perlu membuka hubungan baru pada setiap permintaan. Kedua, route GET /buku didaftarkan seperti pada contoh sebelumnya. Ketiga, db.query(...) mengirimkan perintah SQL ke MySQL. Keempat, kata await menyatakan bahwa program menunggu jawaban database selesai sebelum melanjutkan, sebab database tidak menjawab seketika. Kelima, res.json(rows) mengirimkan baris-baris hasil query sebagai JSON, yaitu bentuk yang Anda lihat sendiri pada Praktik C.

Dua hal kecil layak dijelaskan sekarang agar tidak mengganggu. Tanda kurung siku pada const [rows] ada karena mysql2 mengembalikan dua hal sekaligus, yaitu baris data dan keterangan kolom; kurung siku itu cara mengambil bagian pertama saja. Kata async di depan fungsi diperlukan agar await boleh dipakai di dalamnya. Keduanya dibahas tuntas pada Pertemuan 7.

6.4 Alamat sebagai pertanyaan: route dengan parameter

Berikut kode yang menghasilkan perilaku yang Anda amati pada Praktik C. Perhatikan tanda titik dua pada :id: bagian itu menyatakan bahwa potongan alamat tersebut boleh berisi apa saja, dan nilainya dapat dibaca dari req.params.id.

app.get('/buku/:id', async (req, res) => {
  const [rows] = await db.query(
    'SELECT id, judul, penulis FROM buku WHERE id = ?',
    [req.params.id]
  );

  if (rows.length === 0) {
    return res.status(404).send('Buku tidak ditemukan');
  }

  res.json(rows[0]);
});

Sembilan baris itu memuat empat gagasan yang seluruhnya sudah Anda lihat bekerja pada praktik tadi. Alamat /buku/7 dan /buku/8 ditangani oleh satu route yang sama. Nomor pada alamat dipakai untuk memilih satu baris tertentu di tabel. Bila barisnya tidak ada, server menjawab dengan kode status 404 dan bukan dengan halaman kosong. Dan bila barisnya ada, isinya dikirim sebagai JSON. Bandingkan keempatnya dengan catatan yang Anda buat pada langkah 4 dan 5 Praktik C — perilakunya sama persis.

6.5 Dua kebiasaan aman yang sudah tampak pada kode di atas

Ada dua hal pada kode di atas yang sengaja ditulis dengan cara tertentu, dan alasannya termasuk materi wajib mata kuliah ini. Keduanya dibahas tuntas nanti, tetapi bentuknya perlu Anda kenali sejak sekarang agar tidak terbiasa dengan cara yang salah.

Pertama, tanda tanya pada query. Nilai dari pengguna tidak pernah disambung langsung ke dalam teks query. Yang ditulis adalah tanda tanya sebagai tempat kosong, lalu nilainya diserahkan terpisah dalam kurung siku. Cara ini disebut prepared statement atau parameterized query.

Bandingkan dengan cara yang salah berikut, dan jangan pernah menulis seperti ini: 
// SALAH: nilai dari pengguna disambung langsung ke dalam query
db.query('SELECT * FROM buku WHERE id = ' + req.params.id);
Pada cara yang salah itu, apa pun yang dikirim pengguna menjadi bagian dari perintah SQL yang dijalankan database. Artinya pengguna dapat menyelipkan perintah tambahan untuk membaca atau menghapus tabel lain. Celah ini disebut SQL injection, dan bahasannya ada pada Pertemuan 13. Kebiasaan memakai tanda tanya sebaiknya dibentuk sejak query pertama yang Anda tulis pada Pertemuan 6, bukan ditunda sampai bab keamanan.

Kedua, kata sandi database tidak tertulis di dalam kode. Perhatikan bahwa yang tertulis adalah process.env.DB_PASSWORD, yaitu rujukan ke nilai yang disimpan di luar berkas program, pada sebuah berkas bernama .env. Alasannya sederhana: kode program biasanya ikut terunggah ke tempat berbagi seperti GitHub, sedangkan kata sandi tidak boleh ikut. Cara mengatur berkas .env dibahas pada Pertemuan 11.

Itu bukan soal AI-nya, melainkan soal kode yang diterima tanpa pernah dibaca. Cegahlah dengan kebiasaan sederhana: jangan pernah menempelkan kode yang belum Anda baca sampai selesai.

10. Ringkasan Materi

13. Istilah Kunci Pertemuan 1

Istilah di bawah ini akan dipakai terus-menerus sampai Pertemuan 16. Tidak perlu dihafal kata demi kata, tetapi Anda harus dapat menjelaskan tiap istilah dengan kalimat sendiri, sebab pertanyaan lisan pada checkpoint memakai istilah-istilah ini.

Aplikasi web dinamis
Aplikasi yang halaman atau datanya disusun oleh program pada saat permintaan datang, umumnya dengan mengambil isinya dari database, sehingga tampilannya berubah mengikuti data tanpa ada berkas HTML yang disunting manusia.
Client
Pihak yang meminta. Sepanjang mata kuliah ini client hampir selalu berupa browser, dan client selalu yang memulai satu siklus.
Server
Pihak yang menerima permintaan, mengerjakannya, lalu mengirim jawaban. Server tidak pernah mengirim apa pun sebelum diminta.
localhost
Nama khusus yang selalu menunjuk komputer Anda sendiri. Saat pengembangan, server berjalan di komputer Anda dan diakses lewat nama ini, bukan lewat internet.
Port
Nomor yang membedakan beberapa program yang sama-sama melayani permintaan pada satu komputer. Server latihan mata kuliah ini memakai port 3000.
Path
Bagian alamat sesudah host dan port, misalnya /buku. Path inilah yang dicocokkan Express dengan daftar route-nya.
HTTP
Aturan bersama yang mengatur bentuk permintaan dan jawaban antara browser dan server, sehingga keduanya saling paham meskipun dibuat oleh pihak yang berbeda.
Request
Pesan permintaan dari client, memuat metode, alamat, sekumpulan header, dan pada beberapa metode juga badan pesan.
Response
Pesan jawaban dari server, memuat kode status, sekumpulan header, dan biasanya badan pesan berisi HTML, JSON, gambar, atau berkas lain.
Metode HTTP
Penanda maksud sebuah permintaan: GET mengambil, POST menambah, PUT atau PATCH mengubah, dan DELETE menghapus.
Header
Baris-baris keterangan tambahan pada request atau response, misalnya Content-Type yang memberi tahu jenis isi yang dikirim.
Badan pesan (body)
Isi sesungguhnya dari sebuah pesan. Pada response berupa HTML atau data yang diminta, sedangkan pada POST berupa data yang dikirim pengguna.
Kode status
Angka tiga digit pada response yang menyatakan hasil permintaan: 2xx berhasil, 3xx dialihkan, 4xx salah di sisi permintaan, dan 5xx galat di sisi server.
Stateless
Sifat HTTP yang membuat setiap permintaan berdiri sendiri: server tidak dengan sendirinya mengingat permintaan sebelumnya dari pengguna yang sama.
Cookie
Data kecil yang disimpan browser atas perintah server dan dikirim ulang pada permintaan berikutnya, sehingga server dapat mengenali pengunjung yang sama.
Session
Catatan di sisi server tentang seorang pengguna yang sedang aktif, yang dikaitkan dengan cookie pada browser. Inilah cara fitur login bertahan antarhalaman, dibahas pada Pertemuan 12.
Node.js
Lingkungan yang membuat JavaScript dapat dijalankan di luar browser, sehingga bahasa yang sudah Anda kenal dapat dipakai untuk menulis program server.
npm
Pengelola paket yang datang bersama Node.js, dipakai untuk memasang pustaka seperti Express dan mysql2 serta mencatatnya pada berkas package.json.
Express
Pustaka di atas Node.js yang menyediakan cara ringkas untuk menerima permintaan, mencocokkan alamat dengan route, dan menyusun jawaban.
Route
Pasangan metode dan path beserta fungsi yang menanganinya, misalnya app.get('/buku', ...). Satu path yang sama dengan metode berbeda adalah dua route yang berbeda.
Middleware
Fungsi yang dijalankan di antara masuknya permintaan dan dijalankannya route, misalnya untuk membaca data formulir atau memeriksa apakah pengguna sudah login. Dibahas pada Pertemuan 4.
MySQL
Sistem pengelola database relasional yang dipakai mata kuliah ini untuk menyimpan data secara tahan lama dalam bentuk tabel.
Tabel, baris, kolom
Susunan data pada database relasional: tabel adalah kumpulan data sejenis, satu baris adalah satu data, dan kolom adalah jenis keterangan yang dicatat untuk setiap baris.
SQL
Bahasa untuk berbicara kepada database, misalnya SELECT untuk mengambil dan INSERT untuk menambah data. Mata kuliah ini memakai SQL langsung sebelum mengenal ORM.
Query
Satu perintah SQL yang dikirim server kepada database beserta hasil yang dikembalikannya.
CRUD
Singkatan dari create, read, update, dan delete, yaitu empat perlakuan dasar terhadap data yang menjadi kerangka hampir semua aplikasi.
API
Alamat yang menjawab dengan data, bukan dengan halaman siap tampil. Praktik C memakai API publik untuk melihat bentuk jawaban semacam ini.
JSON
Format penulisan data berbasis teks yang menyerupai objek JavaScript, dipakai luas sebagai isi jawaban API. Dihasilkan oleh res.json().
DevTools
Perangkat bawaan browser untuk memeriksa halaman dan lalu lintas jaringan. Panel Network di dalamnya adalah alat utama praktik hari ini.
Prepared statement
Cara menjalankan query dengan menaruh tanda ? pada tempat nilai, lalu menyerahkan nilainya secara terpisah, sehingga masukan pengguna tidak pernah ikut dibaca sebagai perintah SQL.
SQL injection
Serangan yang memanfaatkan penyambungan masukan pengguna langsung ke dalam teks query, sehingga masukan itu berubah menjadi perintah. Dicegah dengan prepared statement, dibahas pada Pertemuan 13.
Berkas .env
Berkas terpisah tempat menyimpan keterangan rahasia seperti kata sandi database, dibaca program melalui process.env dan tidak diikutsertakan saat kode dibagikan. Dibahas pada Pertemuan 11.
Cara memakai daftar ini. Tutup kolom penjelasannya, lalu jelaskan sendiri setiap istilah dengan satu kalimat. Istilah yang membuat Anda tersendat menandakan bab mana yang perlu dibaca ulang — itu jauh lebih hemat waktu daripada membaca seluruh materi dari awal.
