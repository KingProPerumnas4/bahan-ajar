1. Pengantar: Mengapa Device IoT Perlu Berkomunikasi?

Pada pertemuan-pertemuan sebelumnya, device seperti ESP32 sudah digunakan untuk membaca input dan mengendalikan output. Namun, jika data hanya tinggal di dalam device, nilainya menjadi terbatas. Sistem IoT mulai terasa “terhubung” ketika device dapat mengirim data ke layanan lain, menerima informasi balasan, lalu bertindak berdasarkan hasil komunikasi itu. Di sinilah komunikasi data menjadi inti penting.

HTTP adalah salah satu cara paling mudah untuk memperkenalkan komunikasi data pada IoT karena konsepnya dekat dengan aktivitas sehari-hari di web: meminta halaman, menerima jawaban, mengirim formulir, lalu mendapatkan respons dari server.

Analogi dunia nyata: bayangkan sebuah kantor administrasi. Anda datang ke loket untuk meminta surat keterangan. Anda membawa permintaan, petugas memeriksa, lalu petugas memberikan hasil. Pola ini sama dengan HTTP: ada pihak yang meminta, ada pihak yang melayani, dan ada balasan yang dikirim kembali.

1.1 Posisi HTTP dalam arsitektur IoT

Dalam alur IoT, HTTP biasanya muncul saat device perlu mengirim data ke server web, API, dashboard, atau layanan cloud. Misalnya, sensor suhu virtual membaca nilai, lalu device mengirim nilai itu ke server setiap beberapa detik. Server menerima data, menyimpannya, dan mungkin mengirim respons seperti “data diterima” atau “nilai tidak valid”.

1.2 Apa itu HTTP?

HTTP adalah singkatan dari Hypertext Transfer Protocol. Secara sederhana, HTTP adalah aturan komunikasi yang digunakan ketika satu pihak meminta sesuatu dan pihak lain memberikan jawaban. Di web, browser memakai HTTP untuk meminta halaman. Dalam IoT, device dapat memakai HTTP untuk meminta data, mengirim data sensor, atau berkomunikasi dengan API.

Hal penting yang perlu dipahami adalah HTTP bekerja dengan pola request-response. Artinya, komunikasi dimulai dengan permintaan dari client. Setelah itu server memproses permintaan dan mengirim response. Jadi, dalam model HTTP, device biasanya aktif memulai komunikasi.

2. Konsep Dasar HTTP: Request-Response dan Client-Server

2.1 Model client-server

Pada komunikasi HTTP, ada dua peran utama. Client adalah pihak yang mengirim permintaan. Server adalah pihak yang menerima permintaan, memprosesnya, lalu mengirim jawaban. Dalam konteks IoT, ESP32 sering berperan sebagai client ketika mengirim data ke server. Server bisa berupa API, platform IoT, atau aplikasi web.

Analogi dunia nyata: client-server dapat dibayangkan seperti pelanggan dan restoran. Pelanggan memesan makanan, restoran menerima pesanan, menyiapkan makanan, lalu mengirimkan hasilnya. Pelanggan tidak masuk ke dapur untuk memasak sendiri; ia cukup mengirim permintaan sesuai menu yang tersedia.

2.2 Struktur request

Sebuah request HTTP umumnya memuat metode, alamat tujuan, dan kadang data tambahan. Metode menunjukkan jenis tindakan yang diinginkan. Alamat tujuan menunjukkan ke mana request dikirim. Jika perlu, request juga membawa data, misalnya nilai suhu dalam format JSON.

BagianFungsiContoh sederhana

URL/EndpointMenunjukkan alamat layanan tujuan/api/suhu
HeaderMemberi informasi tambahan tentang requestContent-Type: application/json
BodyMembawa data, biasanya pada POST{"suhu": 28.5}

2.3 Struktur response

Response adalah jawaban dari server setelah request diterima. Response biasanya memuat status dan isi pesan. Status membantu client mengetahui apakah request berhasil atau gagal. Isi pesan bisa berupa teks biasa, JSON, atau data lain.

BagianMakna
Status codeKode hasil proses, misalnya 200 berarti berhasil.
HeaderInformasi tambahan tentang isi response.
BodyIsi balasan, misalnya pesan “OK” atau data JSON.

2.4 Alur request-response

Urutan ini penting: client tidak tiba-tiba menerima data tanpa permintaan. Pada HTTP dasar, data biasanya datang setelah client meminta lebih dulu. Inilah alasan HTTP cocok untuk banyak kebutuhan integrasi sederhana, tetapi kurang ideal untuk komunikasi yang sangat ringan dan harus terus-menerus terjadi secara real-time.

2.5 GET dan POST

GET

GET dipakai ketika client ingin mengambil data dari server. Misalnya device meminta konfigurasi, waktu server, atau nilai tertentu dari API.

POST

POST dipakai ketika client ingin mengirim data ke server. Misalnya device mengirim nilai suhu, status kelembapan, atau informasi sensor lain.

Analogi dunia nyata: GET seperti bertanya kepada petugas, “berapa nomor antrian saya?” Sedangkan POST seperti menyerahkan formulir yang sudah diisi agar diproses lebih lanjut.

3. Data Sederhana: Teks Biasa dan JSON

Dalam komunikasi HTTP, data yang dikirim tidak selalu harus rumit. Pada tahap awal, data bisa berupa teks biasa seperti 28.5 atau pesan sederhana seperti OK. Namun, ketika data mulai bertambah dan perlu diberi label yang jelas, format JSON menjadi lebih berguna.

Teks biasa

Mudah dibaca dan sederhana. Cocok untuk contoh awal atau data tunggal yang tidak kompleks.

28.5
JSON

Memiliki pasangan kunci dan nilai, sehingga lebih rapi untuk banyak data atau integrasi antar sistem.

{
  "suhu": 28.5,
  "ruang": "lab-iot",
  "status": "normal"
}
Analogi dunia nyata: teks biasa seperti menulis angka suhu di secarik kertas. JSON seperti formulir dengan kolom yang jelas: nama ruangan, nilai suhu, dan status. Saat informasi makin banyak, formulir jauh lebih mudah dipahami dibanding catatan acak.

3.1 Mengapa JSON penting?

JSON penting karena data IoT jarang hanya satu nilai saja. Sering kali sebuah device perlu mengirim beberapa informasi sekaligus, misalnya suhu, kelembapan, ID alat, waktu pengiriman, dan status. Dengan JSON, setiap data memiliki nama yang jelas sehingga server atau aplikasi penerima lebih mudah memprosesnya.

3.2 Kapan HTTP cocok digunakan?

  • Saat device perlu mengirim data ke API atau web service secara berkala.
  • Saat komunikasi tidak harus super ringan dan tidak harus selalu real-time.
  • Saat integrasi dengan layanan web menjadi prioritas.
  • Saat struktur komunikasi yang sederhana dan mudah dipahami lebih dibutuhkan.

3.3 Keterbatasan HTTP untuk real-time ringan

Sesuai checkpoint pertemuan ini, Anda perlu memahami bahwa HTTP memiliki keterbatasan untuk real-time ringan. Hal ini karena setiap komunikasi biasanya dimulai dari request baru. Jika data harus sangat sering dikirim oleh banyak device dengan overhead kecil, HTTP tidak selalu paling efisien. Untuk kebutuhan semacam itu, model komunikasi lain seperti MQTT sering lebih sesuai, yang nantinya dibahas pada Pertemuan 7.

4. Implementasi Praktis: Simulasi HTTP Request dari Device

Aktivitas utama pada Pertemuan 6 adalah membuat simulasi HTTP request dari device dan membaca respons sederhana. Skenario yang paling relevan untuk pertemuan ini adalah device virtual mengirim data suhu melalui HTTP secara periodik.

Praktik ini dikerjakan di simulator Wokwi, alat yang sama seperti pada pertemuan-pertemuan sebelumnya, sehingga tidak ada perangkat fisik yang perlu disiapkan. Yang dibangun adalah satu project ESP32 yang menyambung ke jaringan nirkabel simulator, menyusun nilai suhu virtual menjadi data JSON, mengirimnya dengan metode POST, lalu mencetak hasil pengiriman di Serial Monitor. Satu perbedaan penting dari praktik pertemuan sebelumnya perlu Anda sadari sejak awal: hasil praktik kali ini tidak terlihat sebagai lampu yang menyala atau komponen yang bergerak di panel rangkaian, melainkan hanya sebagai tulisan yang muncul di Serial Monitor. Kode lengkapnya ada pada Bab 5, jadi bacalah bab ini dan Bab 5 secara berdampingan.

4.1 Tujuan praktik

  • Melihat bahwa device IoT dapat berkomunikasi dengan layanan luar.
  • Memahami urutan membuat request, menunggu response, lalu membaca hasil.
  • Mengenali bentuk data yang dikirim melalui HTTP.

Komponen yang perlu ditambahkan: tidak ada. Praktik ini hanya memerlukan board ESP32 yang sudah tersedia pada project baru, tanpa LED, resistor, sensor, maupun kabel tambahan, karena nilai suhu tidak dibaca dari sensor melainkan sudah ditetapkan di dalam program sebagai suhuVirtual. Yang menggantikan peran rangkaian pada pertemuan ini adalah dua alat lain, dan keduanya perlu Anda kenali lebih dahulu sebelum kode dijalankan.

Alat pertama: jaringan nirkabel simulator. Jaringan di simulator sudah tersedia dengan sendirinya dan tidak perlu Anda buat, tetapi hanya satu nama yang dikenalinya, yaitu Wokwi-GUEST, dengan kata sandi dibiarkan kosong. Kedua nilai itu sudah tertulis pada konstanta ssid dan password di contoh kode Bab 5, jadi tugas Anda adalah memastikan keduanya tidak diubah, bukan mengisinya dengan nama jaringan tempat Anda berada. Jaringan ini juga hanya hidup selama simulasi berjalan.
Alat kedua: Serial Monitor. Serial Monitor adalah panel di bagian bawah layar, dan pada pertemuan ini ia satu-satunya tempat hasil praktik dapat dibaca. Pastikan panel itu terlihat sebelum tombol jalankan ditekan agar baris pertama, yaitu pesan proses penyambungan jaringan, tidak terlewat. Tidak ada kolom kecepatan yang perlu diatur di panelnya, karena angka pada Serial.begin(115200) di dalam program sudah menentukannya.

4.2 Skenario praktik

ESP32 virtual membaca nilai suhu simulasi. Nilai ini lalu dikirim ke endpoint server menggunakan HTTP POST. Setelah itu, program memeriksa apakah server mengembalikan status berhasil. Proses diulangi secara periodik.

Karena tidak ada kabel yang dipasang, yang perlu Anda pastikan bukan urutan sambungan antar komponen melainkan urutan jalur datanya: nilai suhuVirtual disusun menjadi payload berbentuk JSON, payload itu dikirim melalui objek http ke alamat yang tersimpan pada konstanta serverUrl, dan jalur menuju alamat itu baru terbuka setelah ESP32 tersambung ke jaringan Wokwi-GUEST. Urutan itu tidak boleh dibalik. Bila pengiriman dilakukan sebelum jaringan tersambung, request tidak akan pernah meninggalkan device. Karena itu program pada Bab 5 memanggil WiFi.begin(ssid, password) di dalam setup(), menahan program di dalam while (WiFi.status() != WL_CONNECTED) sampai sambungan benar-benar terjadi, lalu memeriksa sekali lagi dengan if (WiFi.status() == WL_CONNECTED) pada setiap putaran loop() sebelum request disusun.

4.3 Langkah praktik

  1. Siapkan proyek ESP32 di simulator.
  2. Tambahkan kode untuk menghubungkan device ke jaringan Wi-Fi simulasi bila skenario mendukung.
  3. Susun data suhu dalam bentuk teks atau JSON.
  4. Kirim data ke endpoint server menggunakan HTTP.
  5. Baca status code dan isi response.
  6. Ulangi proses secara periodik.

Inti dari praktik ini bukan hanya “berhasil mengirim data”, melainkan memahami alur: siapa yang memulai komunikasi, data apa yang dibawa, bagaimana server menjawab, dan bagaimana device membaca hasil tersebut.

Enam butir di atas dirinci menjadi langkah berikut, yang dikerjakan berurutan di simulator.

  1. Buka wokwi.com di browser, pilih New Project, lalu pilih board ESP32. Project baru sudah berisi board ESP32 dan tidak perlu ditambahi komponen apa pun.
  2. Bila Anda memakai kembali project dari pertemuan sebelumnya, buka tab diagram.json dan tempelkan isi yang tersedia pada Bab 4.2 agar komponen lama tidak ikut terbawa.
  3. Hapus seluruh isi panel kode, lalu tempelkan contoh kode dari Bab 5.
  4. Periksa tiga baris konstanta di bagian atas kode tanpa mengubah nilainya: ssid harus berisi Wokwi-GUEST, password harus tetap kosong, dan serverUrl harus tetap berisi alamat tujuan yang sudah tertulis di sana. Nama jaringan lain atau kata sandi yang diisi akan membuat sambungan gagal.
  5. Pastikan panel Serial Monitor di bagian bawah layar terlihat, lalu tekan tombol jalankan berbentuk segitiga hijau.
  6. Amati tahap penyambungan jaringan lebih dahulu. Baris Menghubungkan ke WiFi... muncul berulang selama sambungan belum terjadi, lalu berhenti dan digantikan satu baris WiFi terhubung. Jangan menilai hasil pengiriman sebelum baris itu muncul, karena selama sambungan belum terjadi program masih tertahan di dalam setup() dan belum mengirim apa pun.
  7. Setelah itu amati pengirimannya. Setiap sekitar lima detik muncul satu baris Kode respon HTTP: beserta angkanya, dan bila angka itu positif menyusul baris Isi respon: beserta balasan dari server. Cocokkan angka yang Anda lihat dengan tabel arti angka di bawah.
  8. Hitung selang waktu antara dua baris Kode respon HTTP: yang berurutan, lalu cocokkan dengan delay(5000) di akhir loop(), sehingga terlihat baris mana yang menentukan seberapa sering data dikirim.
  9. Sebagai langkah variasi, hentikan simulasi, ubah delay(5000) menjadi delay(1000), jalankan kembali, lalu bandingkan kerapatan baris yang muncul dengan pengamatan sebelumnya. Kembalikan ke delay(5000) setelah percobaan ini agar Serial Monitor tetap mudah dibaca.

Angka yang tercetak setelah Kode respon HTTP: adalah satu-satunya tanda apakah pengiriman sampai atau tidak, sehingga arti angka itu perlu Anda kenali sebelum menyimpulkan hasil praktik.

Angka yang terbacaArtinyaYang tampak di Serial Monitor
200, atau angka lain pada kelompok 2xx Request sampai ke server dan diproses tanpa masalah. Inilah kode status keberhasilan. Baris Isi respon: ikut muncul beserta balasan dari server.
Kelompok 4xx, misalnya 404 Request sampai ke server, tetapi server menolaknya. Pada 404, jalur yang diminta tidak dikenali oleh server tujuan. Baris Isi respon: tetap muncul karena angkanya positif, tetapi isinya pesan penolakan, bukan tanda data tersimpan.
Kelompok 5xx Request sampai dan dikenali, tetapi server gagal memprosesnya. Masalahnya ada di sisi server, bukan di program Anda. Sama seperti 4xx: angkanya positif sehingga isi respon tetap dibaca dan dicetak.
Angka negatif, misalnya -1 Ini bukan kode status HTTP. Angka negatif berasal dari HTTPClient dan berarti request tidak pernah sampai ke server, biasanya karena jaringan belum benar-benar tersambung atau alamat tujuan tidak dapat dicapai. Baris Isi respon: tidak muncul sama sekali, karena syarat if (httpResponseCode > 0) tidak terpenuhi.

Bedakan dengan tegas dua hal yang sering tertukar. Angka positif berarti request berhasil keluar dari device dan dijawab oleh pihak di seberang, sedangkan angka negatif berarti request tidak pernah keluar. Perbedaan itu adalah pemeriksaan pertama setiap kali hasil pengiriman terasa tidak sesuai harapan.

Angka yang bukan 200 belum tentu berarti program Anda salah. Alamat pada serverUrl di Bab 5 dipakai sebagai contoh tujuan, bukan sebagai layanan pencatat data yang benar-benar menyimpan nilai suhu. Bila alamat tujuan tidak menyediakan jalur yang menerima POST, yang kembali adalah angka pada kelompok 4xx, dan untuk memahami alur request-response hal itu sudah cukup karena seluruh tahap pada Bab 2.4 tetap terjadi dan tetap terbaca. Bila tugas pada Bab 8.2 menuntut kode status keberhasilan, alamat tujuan perlu diganti dengan layanan yang memang menyediakan jalur penerima POST; nilai ssid dan password tetap tidak berubah.

Hasil yang harus terlihat: Serial Monitor menampilkan beberapa baris Menghubungkan ke WiFi..., lalu satu baris WiFi terhubung yang menandai sambungan ke Wokwi-GUEST sudah benar-benar terjadi. Sesudah itu muncul pasangan baris yang berulang dengan jarak sekitar lima detik: satu baris Kode respon HTTP: beserta angkanya, dan bila angka itu positif satu baris Isi respon: beserta balasan server. Pola berulang inilah bukti pengiriman berjalan periodik, bukan sekali jalan, dan angka positif yang muncul pada setiap putaran adalah bukti request benar-benar keluar dari device dan dijawab. Setelah delay(5000) diubah menjadi delay(1000), jarak antar pasangan baris menjadi jauh lebih rapat. Di situlah terlihat bahwa satu angka di dalam program menentukan seberapa sering sebuah device melaporkan datanya.

Baris Menghubungkan ke WiFi... muncul terus tanpa pernah berhenti. Ini kegagalan yang paling sering terjadi pada pertemuan ini, dan gejalanya khas: baris itu tercetak berulang tanpa pernah disusul WiFi terhubung, sedangkan baris Kode respon HTTP: tidak pernah muncul sama sekali karena program masih tertahan di dalam setup(). Periksa tiga hal berurutan. Pertama, nama jaringan pada ssid harus tertulis tepat sebagai Wokwi-GUEST, termasuk huruf besar dan tanda hubungnya. Kedua, isi password harus dibiarkan kosong dan bukan diisi kata sandi apa pun. Ketiga, simulasi harus dalam keadaan berjalan, karena jaringan simulator hanya tersedia selama simulasi hidup dan tidak dapat dicoba tanpa menjalankan program.

5. Contoh Kode HTTP Client pada ESP32

Contoh berikut menunjukkan pola sederhana ketika ESP32 mengirim data suhu virtual dengan HTTP POST. Kode ini bersifat dasar dan dipakai untuk membantu Anda memahami alur program, bukan untuk menekankan detail library tertentu di luar tujuan Pertemuan 6.

#include <WiFi.h>
#include <HTTPClient.h>

const char* ssid = "Wokwi-GUEST";
const char* password = "";
const char* serverUrl = "http://example.com/api/suhu";

float suhuVirtual = 28.5;

void setup() {
  Serial.begin(115200);
  WiFi.begin(ssid, password);

  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.println("Menghubungkan ke WiFi...");
  }

  Serial.println("WiFi terhubung");
}

void loop() {
  if (WiFi.status() == WL_CONNECTED) {
    HTTPClient http;
    http.begin(serverUrl);
    http.addHeader("Content-Type", "application/json");

    String payload = "{\"suhu\":" + String(suhuVirtual) + "}";
    int httpResponseCode = http.POST(payload);

    Serial.print("Kode respon HTTP: ");
    Serial.println(httpResponseCode);

    if (httpResponseCode > 0) {
      String response = http.getString();
      Serial.println("Isi respon:");
      Serial.println(response);
    }

    http.end();
  }

  delay(5000);
}

5.1 Penjelasan struktur kode

Kode ini dapat dipahami sebagai lima tahap utama: menyiapkan library, mendefinisikan koneksi dan alamat server, menghubungkan Wi-Fi, membuat request HTTP, lalu membaca response.

5.2 Penjelasan baris per baris

5.3 Penjelasan alur kode secara utuh

Saat program dimulai, ESP32 terlebih dahulu membuka komunikasi serial agar pesan dapat dilihat pada monitor. Kemudian device mencoba terhubung ke jaringan. Setelah berhasil terhubung, program masuk ke loop(). Pada setiap putaran, jika koneksi masih tersedia, device membuat objek HTTP, menentukan alamat server, menyusun payload JSON berisi suhu virtual, lalu mengirimkannya dengan metode POST.

Setelah request dikirim, server mengembalikan response code. Jika nilainya positif, device kemudian membaca isi response dan menampilkannya ke Serial Monitor. Setelah proses selesai, koneksi HTTP ditutup melalui http.end(), lalu program menunggu lima detik untuk mengirim data berikutnya.

5.4 Hubungan kode dengan teori

Kode ini adalah contoh langsung dari teori client-server. ESP32 berperan sebagai client karena ia yang memulai request. Server berperan sebagai pihak yang menerima data dan mengirim jawaban. Metode POST dipilih karena tujuan komunikasi adalah mengirim data suhu. JSON dipilih karena lebih rapi daripada teks biasa ketika sistem mulai berkembang.

5.5 Bagaimana jika memakai GET?

Jika GET digunakan, umumnya device bukan mengirim body JSON, melainkan meminta informasi dari server. Misalnya, device ingin mengambil nilai ambang batas suhu dari server. Jadi, pemilihan GET atau POST bergantung pada arah tujuan komunikasi: mengambil data atau mengirim data.

6. Menghubungkan Materi Ini dengan Sistem IoT yang Lebih Besar

Pertemuan 6 adalah jembatan penting antara device lokal dan sistem terhubung. Sampai tahap ini, Anda telah melihat input, output, sensor, aktuator, struktur program, dan debugging dasar. Kini device mulai berinteraksi dengan layanan luar. Ini berarti IoT tidak lagi sekadar program yang berjalan sendiri, melainkan bagian dari ekosistem data.

Dari sensor ke data
Nilai sensor tidak berhenti di device, tetapi dapat dikirim ke server.
Dari device ke layanan
Device belajar “berbicara” dengan platform luar melalui protokol HTTP.
Dari lokal ke terhubung
Sistem mulai bergerak dari eksperimen lokal menuju integrasi yang lebih luas.
Analogi dunia nyata: sebelumnya device seperti orang yang belajar sendiri di kamar tanpa melaporkan apa pun. Dengan HTTP, ia mulai mengirim laporan ke sistem administrasi pusat. Artinya, aktivitas lokal kini menjadi bagian dari sistem yang lebih besar dan dapat dipantau pihak lain.

7. Ringkasan Materi

  • HTTP adalah protokol komunikasi berbasis request-response.
  • Dalam model HTTP, client mengirim request dan server memberi response.
  • GET dipakai untuk mengambil data, sedangkan POST dipakai untuk mengirim data.
  • Data dapat dikirim dalam format teks biasa atau JSON, dan JSON lebih cocok saat data mulai kompleks.
  • HTTP cocok untuk banyak integrasi sederhana pada IoT, tetapi memiliki keterbatasan untuk real-time ringan karena model komunikasinya tidak seefisien protokol yang lebih ringan.
  • ESP32 dapat berperan sebagai HTTP client yang mengirim data suhu virtual secara periodik dan membaca response dari server.

Materi ini mencakup fokus, aktivitas, target minimum, tugas latihan, dan checkpoint Pertemuan 6.
